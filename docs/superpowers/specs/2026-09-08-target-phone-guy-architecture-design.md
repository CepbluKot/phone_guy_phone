# Целевая архитектура Phone Guy

Статус: проектное решение для реализации  
Дата: 2026-09-08  
Ветка: `main`  
Целевой движок: GPT v2 (`/ws/rvc-v2`, hop 1 с, context 0,5 с, lookahead 0,1 с)  
Canary и резерв: `infer/rtrvc.py`, FCPE, block 0,3 с

## Как исполнителю пользоваться этой спецификацией

Это источник истины для следующего implementation plan. Исполнитель работает
строго по этапам A–E, на каждом этапе сначала пишет тест, затем минимальную
реализацию, затем проводит указанную живую проверку. Нельзя объявлять этап
готовым только по unit-тестам или только по статусу процесса.

Если код, старая документация и эта спецификация расходятся, исполнитель
сначала фиксирует расхождение. Тихо менять зафиксированные решения раздела 2
нельзя: изменение целевого движка, raw-fallback, публичного доступа,
параллелизма или хранения аудио требует новой версии спецификации.

Перед любым изменением VM209 нужно снять read-only baseline. Существующие
несвязанные изменения в Git, VM208/Frigate и чужие worktree сохраняются.

## 1. Задача

Превратить текущие рабочие демонстрации в постоянную приватную телефонную
систему. Несколько участников должны подключаться к Asterisk через VPN. Для
каждого SIP-номера задаётся профиль `original` или `phone-guy`. Голос участника
с профилем `phone-guy` проходит через выбранную модель GPT v2, и остальные
участники слышат только обработанный результат. Исходный голос этого участника
не должен попадать в общий разговор даже при отказе модели.

Система должна переживать перезапуск VM209, развёртываться из Git, иметь
проверяемый откат и не зависеть от процессов или файлов в `/tmp`.

## 2. Зафиксированные решения

1. Качественный целевой голос — уже выбранный пользователем GPT v2 из
   `rvc_service/server.py`, endpoint `/ws/rvc-v2`.
2. `v2-fcpe` остаётся отдельным canary для сравнений и резервом, но не участвует
   в обычном звонке.
3. Основной домен — `voice.lan.awesomeio.ru`; доступ только через VPN и
   приватный DNS.
4. Asterisk — центр звонков и конференций. RVC не управляет звонками, а только
   преобразует один аудиопоток.
5. Привязка голоса выполняется по SIP-идентичности: `extension → profile`.
6. В первой версии одновременно разрешён один говорящий с профилем
   `phone-guy`. Остальные участники могут говорить исходными голосами.
7. При ошибке RVC используется fail-closed: raw-голос не пропускается.
8. Аудио и транскрипты не сохраняются. Внешние облачные сервисы не используются.
9. Требование задержки менее 150 мс не входит в объём. Приоритет — выбранное
   пользователем звучание и устойчивый непрерывный поток.
10. VM208/Frigate, её ресурсы и конфигурация не изменяются.

## 3. Не входит в первую реализацию

- установка компьютера, микрофона и динамика внутрь физического телефона;
- доступ к SIP/Asterisk напрямую из публичного интернета;
- мобильная телефонная сеть, PSTN и реальные телефонные номера;
- несколько одновременно работающих AI-голосов;
- обучение или замена модели Phone Guy;
- браузерная админ-панель для маршрутов — сначала достаточно версионируемого
  конфигурационного файла;
- автоматический выбор между GPT v2 и FCPE по нагрузке;
- запись разговоров, распознавание речи и генерация текстовых ответов.

## 4. Текущее состояние и разрыв

Уже существует:

- `voice-rvc.service` на VM209, `127.0.0.1:8090`, с v1 и GPT v2;
- приватные WSS-маршруты `/ws/rvc` и `/ws/rvc-v2`;
- Asterisk и conference-controller на `127.0.0.1:8092` и `8091`;
- клиент `conference/rvc.py`, уже переведённый на GPT v2;
- исследовательский `rvc_service/rt_server.py` с FCPE, TTS и сравнениями;
- браузерные демонстрации и тестовые виртуальные участники.

Не готово:

- исследовательский контур запускается из `/tmp` и сейчас фактически не
  работает, несмотря на сохранённый Caddy-маршрут;
- нет постоянной службы FCPE-canary;
- нет SIP-учётных записей реальных клиентов и PJSIP-конфигурации;
- нет таблицы `extension → voice profile` как источника истины;
- текущая конференция является слушательским стендом с синтетическими
  участниками, а не полноценным двусторонним звонком;
- нет продакшен-пути, который изолирует raw-канал AI-участника и возвращает в
  ConfBridge только преобразованное аудио;
- документация RND описывает снятые варианты и расходится с актуальным кодом.

## 5. Целевая схема

```text
SIP-клиенты через WireGuard
  │
  ▼
Asterisk / PJSIP
  │
  ├─ profile=original ───────────────────────────────┐
  │                                                  │
  └─ profile=phone-guy                               │
       │                                             │
       ▼                                             │
     private source bridge                           │
       │                                             │
       ▼                                             │
     conference-controller                           │
       │ PCM16 mono 48 kHz / 20 ms                   │
       ▼                                             │
     voice-rvc.service :8090 /ws/rvc-v2              │
       │ processed PCM16                             │
       ▼                                             │
     injected processed channel ─────────────────────┤
                                                     ▼
                                              main ConfBridge
                                                     │
                                                     ▼
                                           динамики участников

Отдельно, не в боевом звонке:
voice-rtrvc-canary.service :8093 → v2-fcpe / сравнение / TTS
```

## 6. Компоненты

### 6.1 Asterisk

Asterisk отвечает за регистрацию SIP-клиентов, установление звонков,
конференц-комнаты и смешивание аудио. Он не знает деталей RVC-модели.

Добавляются:

- PJSIP endpoints для внутренних номеров `201`, `202`, `203`;
- номер конференции, например `600`;
- Stasis/ARI-маршрут для каналов, которым назначена обработка;
- ограниченный RTP-диапазон только для VPN/LAN;
- отдельные секреты клиентов вне Git.

SIP-клиенты подключаются только через WireGuard. Публичные `5060` и RTP-порты
не открываются.

### 6.2 Voice routing

Источник истины: `deploy/voice-routing.yaml`.

```yaml
schema_version: 1
extensions:
  "201": original
  "202": phone-guy
  "203": original
profiles:
  original:
    pipeline: passthrough
  phone-guy:
    pipeline: rvc
    endpoint: ws://127.0.0.1:8090/ws/rvc-v2
```

Контроллер загружает файл при старте и валидирует его до открытия healthcheck.
В первой версии любой неизвестный extension отклоняется: неявного профиля и
общего fallback-правила нет.

Конфигурация не должна содержать SIP-пароли. Для изменения голоса оператор
правит одну строку, выполняет проверку конфигурации и перезапускает только
controller, не Asterisk и не RVC.

### 6.3 Conference controller

Контроллер связывает ARI, аудиоканал и RVC:

1. Получает событие входа SIP-канала.
2. Определяет extension и профиль.
3. Для `original` помещает канал прямо в основной ConfBridge.
4. Для `phone-guy` не помещает исходный канал в основной мост.
5. Создаёт private source bridge и ExternalMedia-каналы ввода/вывода.
6. Передаёт 20-мс PCM-кадры в `RvcStream` GPT v2.
7. Валидирует метаданные, порядок сэмплов и размер каждого ответа.
8. Вставляет только обработанный канал в основной ConfBridge.
9. При завершении звонка закрывает WebSocket, RTP и ARI-ресурсы идемпотентно.

Для одного SIP-участника существует ровно один session object. Состояние
сессии не разделяется между звонками.

### 6.4 Основной RVC-сервис

`voice-rvc.service` остаётся единственным боевым GPU-воркером. Его контракт:

- loopback-only `127.0.0.1:8090`;
- WebSocket `/ws/rvc-v2`;
- 48 кГц, mono, PCM16LE;
- входные кадры 20 мс;
- выходные блоки по 1 секунде;
- один активный AI-сеанс;
- bounded input queue и явные `busy`, `overloaded`, `stalled`;
- v1 сохраняется на время миграции и отката, но новые клиенты его не используют.

Вес модели, индекс и upstream checkout хранятся вне Git в уже существующем
`/opt/voice-changer/experiments/phoneguy`. Release-код неизменяем и выбирается
symlink `/opt/voice-rvc/current`.

### 6.5 FCPE canary

RND-код переносится из `/tmp/rt_demo` в управляемый release-каталог
`/opt/voice-rtrvc/releases/<stamp>` и запускается службой
`voice-rtrvc-canary.service` на `127.0.0.1:8093`.

Canary:

- загружает только `v2-fcpe`, block 0,3 с;
- не участвует в Asterisk-маршруте;
- доступен через отдельный приватный URL для A/B;
- использует собственный лимит памяти и единый GPU lock внутри процесса;
- не запускает отдельную копию GPT на `8098`;
- может быть остановлен без влияния на звонки.

Страница GPT-сравнения должна обращаться к боевому `/ws/rvc-v2`, а не к
дублирующему процессу на `8098`. Это освобождает VRAM и устраняет временный
research-компонент.

### 6.6 Web UI

`voice.lan.awesomeio.ru` предоставляет:

- страницу проверки GPT v2 с микрофоном;
- страницу прослушивания конференции;
- короткую инструкцию подключения SIP-клиента;
- отображение `busy`, прогрева и недоступности без технического traceback.

Сравнительная страница показывает два подтверждённых варианта: GPT v2 и
FCPE-canary. Снятые RMVPE/FCPE-fast варианты в целевом UI не возвращаются.

## 7. Потоки данных

### 7.1 Обычный участник

`SIP/RTP → Asterisk → main ConfBridge → остальные участники`.

Контроллер не копирует и не сохраняет звук.

### 7.2 Участник Phone Guy

`SIP/RTP → private bridge → controller → GPT v2 → processed media channel → main ConfBridge`.

Raw source channel никогда не состоит в main ConfBridge. Это структурная
гарантия против утечки исходного голоса, а не условие внутри одного callback.

### 7.3 Обратный звук участнику

Участник Phone Guy получает обычный микс main ConfBridge без собственного
raw-голоса. Локальное sidetone/эхо контролируется SIP-клиентом и звуковым
устройством, а не RVC.

## 8. Ошибки и безопасное поведение

| Событие | Поведение |
| --- | --- |
| RVC прогревается | Участник ждёт; UI/тон сообщает о подготовке. Raw не проходит. |
| RVC занят | Второй `phone-guy` канал не подключается; понятный busy. |
| RVC timeout/stall | AI-канал удаляется из мостов и остаётся подключённым без исходящего голоса; его SIP-клиент получает служебный тон ошибки. Original-участники продолжают разговор. |
| Некорректный блок/метаданные | Сессия немедленно закрывается; повреждённое аудио не инжектируется. |
| Controller restart | Asterisk остаётся жив; обрабатываемые каналы завершаются fail-closed и могут переподключиться. |
| Canary упал | Боевой звонок и GPT v2 не затрагиваются. |
| Asterisk restart | SIP-клиенты регистрируются повторно; RVC продолжает работать. |
| Перезагрузка VM209 | systemd и Compose восстанавливают все production-компоненты автоматически. |

Автоматического raw fallback для `phone-guy` нет. Если позже он понадобится,
это отдельное продуктовое решение и новая версия спецификации.

## 9. Ресурсы и параллелизм

- GPT v2: один активный преобразуемый поток.
- FCPE-canary: отдельный процесс, не нужен для доступности звонков.
- TTS и batch compare не должны вытеснять живой звонок. Они возвращают `busy`,
  пока занят production RVC; фоновой очереди для них нет.
- Запрещено поднимать третью полную копию модели на GTX 1050 Ti: измерения RND
  уже показали CUDA OOM при дополнительном процессе.
- CPU/RAM VM209 не считаются средством уменьшения задержки; GPU остаётся узким
  местом.

## 10. Развёртывание

### 10.1 Постоянная раскладка VM209

```text
/opt/voice-rvc/releases/<stamp>/          основной GPT v2 код
/opt/voice-rvc/current -> releases/...   активный GPT v2 release
/opt/voice-rtrvc/releases/<stamp>/       FCPE canary код
/opt/voice-rtrvc/current -> releases/... активный canary release
/opt/voice-conference/releases/<stamp>/  Asterisk/controller release
/opt/voice-routing/voice-routing.yaml    маршруты без секретов
/run/voice-secrets/                      runtime secrets, не Git
```

Службы:

- `voice-rvc.service` — production GPT v2;
- `voice-rtrvc-canary.service` — FCPE canary;
- `voice-conference` Compose project — Asterisk и controller;
- `caddy.service` — TLS и приватная маршрутизация.

### 10.2 Требования к deploy-скриптам

Каждый deploy обязан:

1. Проверить clean/ожидаемый source commit и все локальные тесты.
2. Проверить свободную RAM/VRAM и состояние существующих сервисов.
3. Создать immutable release и резервную копию изменяемых конфигураций.
4. Развернуть новый компонент без остановки несвязанных компонентов.
5. Проверить loopback health и синтетический аудиопоток.
6. Валидировать Caddy/Asterisk-конфигурацию до reload.
7. Проверить приватный HTTPS/WSS и реальный SIP-сценарий.
8. При любой ошибке автоматически вернуть symlink/image/config предыдущего
   релиза и доказать его здоровье.

Deploy RVC не меняет conference, DNS, firewall, Proxmox и Frigate. Deploy
conference не переустанавливает RVC-модель. Canary deploy не перезапускает
production GPT v2.

## 11. Безопасность и приватность

- Все пользовательские endpoints доступны только из VPN/LAN.
- Сервисы слушают loopback; наружу публикуется только Caddy на приватном IP.
- SIP credentials и ARI password создаются отдельно, права не шире `0600`, в
  Git и логи не попадают.
- Origin для WebSocket проверяется по allowlist.
- Upload, WebSocket frame, очереди, длительность и число сессий ограничены.
- Контейнеры остаются read-only, без capabilities, с `no-new-privileges`.
- systemd-сервисы сохраняют `ProtectSystem`, `ProtectHome`, memory/CPU limits и
  network allowlist.
- PCM, WAV и текст TTS не журналируются. В логах только session id, длительность,
  состояние и метрики без содержимого.

## 12. Наблюдаемость

Каждый production-компонент предоставляет health endpoint со статусом без
секретов. Для активной AI-сессии нужны метрики:

- session state и выбранный профиль;
- processing p50/p95 и RTF;
- queue depth и max outstanding blocks;
- underruns/overloads/timeouts;
- число активных SIP-каналов и AI-каналов;
- service restart count;
- RAM и GPU memory high-water mark.

Нельзя считать систему исправной только по `active (running)`: smoke обязан
передать ненулевой PCM через полный путь и проверить непрерывность sample index.

## 13. Этапы реализации

### Этап A — стабилизировать выбранный GPT v2

- сделать `/ws/rvc-v2` единственным endpoint новых клиентов;
- сохранить v1 только для rollback;
- проверить restart, reconnect, busy и 5-минутный поток;
- зафиксировать фактические latency/RTF/VRAM в live status.

### Этап B — продуктировать FCPE-canary

- удалить зависимость от `/tmp` и процесса `8098`;
- добавить systemd unit, release layout, scoped deploy и rollback;
- оставить только `v2-fcpe` и необходимые сравнения;
- проверить, что остановка canary не влияет на GPT v2 и conference.

### Этап C — добавить SIP identities и routing config

- создать PJSIP-конфигурацию и секреты для `201–203`;
- реализовать строгий parser `voice-routing.yaml`;
- добавить диагностический вывод effective routing без секретов;
- проверить регистрацию только через VPN.

### Этап D — реализовать двусторонний routed call

- разделить raw и processed bridges;
- связать один `phone-guy` канал с `RvcStream` v2;
- возвращать processed media в main ConfBridge;
- реализовать cleanup и fail-closed для каждого отказа;
- сохранить обычные `original` каналы без RVC.

### Этап E — провести приёмку и переключить целевой сценарий

- выполнить звонок Linux-телефон ↔ операторский SIP-клиент;
- затем добавить третьего участника;
- проверить профиль `202 → phone-guy`, `201/203 → original`;
- провести soak, перезапуски и rollback drill;
- обновить `START_HERE`, `HANDOFF`, `LIVE_STATUS`, `OPERATIONS` и убрать
  утверждения о снятых RND-вариантах.

Этапы идут последовательно. Каждый этап должен иметь отдельный обратимый commit
и собственные доказательства приёмки до перехода к следующему.

## 14. Проверки и критерии приёмки

### 14.1 Автоматические

- unit-тесты voice routing: допустимые профили, неизвестные extensions,
  дубликаты, повреждённый YAML;
- contract-тесты GPT v2: start/ready/metrics/binary/stop, строгие размеры;
- session-тесты: raw channel никогда не добавляется в main bridge для
  `phone-guy`;
- cleanup-тесты для disconnect, timeout, cancellation и controller restart;
- busy-тест двух AI-участников;
- passthrough-тест нескольких `original` участников;
- deploy/rollback-тесты с фиктивным root prefix;
- браузерные тесты ошибок, разрешения микрофона и остановки;
- конфигурационные тесты Caddy, Asterisk, Compose и systemd hardening.

### 14.2 Живые

1. `201 original` и `202 phone-guy` регистрируются через VPN.
2. Оба входят в комнату `600` и слышат друг друга.
3. Участник `201` слышит от `202` только Phone Guy; raw-копии нет.
4. Участник `202` слышит исходный голос `201`.
5. Третий `203 original` входит и слышит тот же корректный микс.
6. Попытка второго `phone-guy` получает busy без утечки raw.
7. Остановка RVC во время речи не выпускает raw и не ломает original-каналы.
8. После restart RVC/controller/Asterisk система восстанавливается без ручного
   запуска процессов из `/tmp`.
9. Пяти минут непрерывной речи хватает без роста очереди, утечки памяти,
   рестартов и рассинхронизации sample timeline.
10. Rollback возвращает предыдущий рабочий звонок и подтверждается повторением
    пунктов 1–4.

## 15. Definition of Done

Архитектура считается реализованной только когда одновременно выполнено всё:

- GPT v2 обслуживает основной Phone Guy-маршрут;
- FCPE доступен как независимый управляемый canary;
- процессы `8093/8098` из `/tmp` больше не являются зависимостями;
- SIP-участники подключаются через VPN и получают профиль по extension;
