# Аудит и оптимизация проекта — план

> **Для исполнителя:** идти по фазам по порядку. Каждая фаза — отдельная ограниченная задача; после неё обновить Execution State внизу (заменять, а не дописывать). Не считать устаревшие замеры (2026-09-07) текущими.

**Цель:** найти слабые и медленные места, баги, дублирующийся и мёртвый код ("слоп"), и сделать проект быстрее и компактнее без изменения внешнего поведения.

**Не цели:** новые функции; смена целевого голоса/движка (GPT v2, `/ws/rvc-v2`); переписывание архитектуры; изменения VM208/Frigate; публичный доступ без VPN.

- Правила `AGENTS.md`, `docs/AI_EXECUTION_WORKFLOW.md` и проектные правила безопасности/деплоя главнее этого плана.
- Перед стартом: `git worktree list`, `git branch -a`. ## Фаза 0 — базовая линия (read-only)

1. Зафиксировать HEAD, ворктри, версии Go/Python/Node.
2. Запустить существующие проверки и записать результат и время: `go build ./... && go vet ./... && go test ./...`, `pytest`, Node-тесты клиента, сборка `admin-ui`.
3. Снять базовые метрики: размер Docker-образов, размер бандла `admin-ui`, время тестов, `go test -race` на `internal/calls` и `internal/ari`.

**Критерий:** таблица «проверка → результат/время» без правок кода.

## Фаза 1 — поиск (read-only, без правок)

Для каждой области из карты собрать находки в `docs/AUDIT_2026-10-24.md` (формат как в `docs/AUDIT_2026-09-06.md`: приоритет, дефект, `файл:строка`, предложенное исправление). Обязательные проходы:

- **Баги и надёжность:** гонки (`-race`), утечки горутин/соединений/файловых дескрипторов, необработанные ошибки, отсутствие таймаутов/контекстов, граничные случаи в ARI/SIP, reconnect-логика WebSocket.
- **Производительность:** горячий путь аудио (кадры 20 мс): аллокации на кадр, копии, блокировки, логирование в цикле; Python — синхронный код в event loop, лишние `.cpu()/.numpy()`, повторная загрузка моделей; веб — лишние ререндеры, размер бандла, кэш-заголовки.
- **Слоп и дубли:** повторяющиеся функции между `internal/`, `conference/`, `selfmonitor/`, `rvc_service/`; закомментированный код; неиспользуемые экспорты, флаги, env-переменные, зависимости (`go mod tidy` diff, `pip` vs `requirements.lock`, `npm ls`/`depcheck`); избыточные комментарии и обёртки без смысла.
- **Скрипты и деплой:** дубли в `deploy/*.sh`, неидемпотентность, жёстко прошитые значения, расхождение репозитория с рантаймом (учесть runtime-only SIP-эндпоинты — см. коммит `7e7566c`).
- **Безопасность (быстрый проход):** секреты в репозитории/логах, открытые порты, валидация входа, Origin/CORS, права контейнеров. Глубокий разбор — отдельным `/security-review`.
- **Репозиторий:** крупные бинарники в `experiments/` (WAV ~150k «строк»), устаревшие доки.

Каждая находка: оценка эффекта (латентность/размер/риск) и риска правки. Сортировка по «эффект / риск».

**Критерий:** `docs/AUDIT_2026-10-24.md` с приоритизированным списком; ни одной правки в коде.

## Фаза 3 — исправления (малыми партиями)

Порядок: (1) баги/гонки/утечки → (2) горячий путь и латентность → (3) удаление мёртвого кода и дублей → (4) зависимости и размер образов/бандла → (5) скрипты деплоя → (6) репозиторий и документы.

Правила партии:
- Одна тема — один коммит; до и после — те же тесты; для оптимизаций — измерение «до/после» в сообщении коммита.
- Для бага сначала падающий тест, потом исправление.
- Не менять поведение при «чистке»; если тестов нет — добавить характеризующий тест до удаления.
- Не коммитить чужие незакоммиченные правки.

### Образец CI/CD — уточнено по `gitlab.com/proactive-monitoring` (read-only)

Берём именно эту схему (в ней 16 проектов: сервисы, воркеры, `frontend`, `airflow-dags`, `deployment`):

- **Шаблоны живут в проекте `deployment`**, каталог `ci/gitlab/`: `pipeline.yml` (общий workflow), `python-service.yml`, `node.yml`, `python.yml`, `docker-build.yml`, `deploy-service.yml`, `version.yml`, `tools.yml`, `ci-deps.yml` и каталог `services/` с тонким файлом на каждый сервис (`services/frontend.yml`, `services/forecast.yml`, …).
- **В сервисных проектах нет `.gitlab-ci.yml`.** Вместо него в настройках проекта задан `ci_config_path = ci/gitlab/services/<имя>.yml@<группа>/deployment:<SHA коммита>`. То есть версия шаблона закрепляется SHA; обновление шаблона = осознанная смена pin в каждом проекте.
- Сам `deployment` проверяется своим `.gitlab-ci.yml` с `include: local` (MR проверяется против той ревизии шаблонов, которую меняет): `policy-tests` (pytest), `shellcheck --severity=error`, `check-locks`. Образы не собирает и кластера не трогает.
- **`pipeline.yml`:** `workflow.rules` с белым списком проектов группы; форк-MR запрещены; пайплайн запускается на MR, теги релизов, push в защищённую default-ветку и ручной `web`; `auto_cancel on_new_commit: interruptible`; `retry` только при `runner_system_failure`; тег раннера задаётся переменной `PM_CI_RUNNER_TAG`; `GET_SOURCES_ATTEMPTS=3`.
- **Единые стадии у всех сервисов:** `quality → test (у фронта unit) → image → deploy → release`. Для Python: `ruff-check`, `ty-check`, `code-quality`, `unit-tests` (`compileall` + `pytest`); для фронта: `quality` (`tsc --noEmit`), `build-bundle`, `unit` с `parallel: 4`. Сервисный файл только задаёт переменные (`PM_PY_RUFF_PATHS`, `PM_PY_TY_PATHS`, `PM_PY_PYTEST_ARGS`, `PM_IMAGE_NAME`) и, где нужно, переопределяет документированный хук.
- **Образ:** `ci-deps-image` печёт образ зависимостей CI (пересборка по хешу lock-файлов), `build-image` на MR — проверочная сборка через общий BuildKit без push (`resource_group`), с импортом кэша слоёв из `:latest`. Образ реально собирается и публикуется только `build-production-image` при деплое.
- **Деплой и релиз:** `deploy-production` зависит от образа и от всех проверок сервиса; версии существуют только как теги релиза `X.Y.Z` (создаются вручную или через API), ни один файл версию не хранит.
- **Секреты:** только CI/CD variables группы (masked/protected); токен задачи `CI_JOB_TOKEN` для приватных пакетов.

### Применение к нашим репозиториям

Проект `deploy` — наш `deployment`: он хранит `ci/gitlab/` и проверяется своим `.gitlab-ci.yml` (`shellcheck`, `docker compose config`, `terraform validate`, pytest шаблонов). Остальные проекты получают `ci_config_path` с закреплённым SHA на свой файл `ci/gitlab/services/<имя>.yml`.

| Репозиторий | Файл шаблона | Что запускает |
| --- | --- | --- |
| `voice-web` | `services/voice-web.yml` + `go.yml` | quality (`go vet`, `staticcheck`) → test (`go test -race`) → image |
| `rvc-service`, `conference-service`, `selfmonitor` | `services/<имя>.yml` + `python-service.yml` | quality (`ruff`) → test (`compileall` + `pytest`) → image; зависимости из `requirements.lock` с `--require-hashes` |
| `frontend` | `services/frontend.yml` + `node.yml` | quality (`tsc`/lint) → unit (Node-тесты, шардирование) → build-bundle → image |
| `deploy` | локальный `.gitlab-ci.yml` | policy-tests, shellcheck, check-locks |
| `docs`, `experiments` | `services/docs.yml` | проверка ссылок и размера файлов |

Чего у нас нет и что приходится решать иначе: у них свои Kubernetes-раннеры, BuildKit и реестр `images.lan.awesomeio.ru:5002`. У нас стартуем с shared runners gitlab.com (или раннером на домашнем хосте) и образами в GitLab Container Registry; `deploy-production` пока только ручной (`when: manual`) без доступа к VM209 из CI.

4. **Перенос кода с историей.** Для каждого репозитория — `git filter-repo --path <каталоги>` из свежего клона (`--force` только в клоне, исходный репозиторий не трогать), затем push в GitLab. Крупные WAV из `experiments/` — через LFS или без истории.
5. **Добавить в каждый репозиторий:** `.gitlab-ci.yml` (include с закреплённым SHA), `README.md`, `PROVENANCE.md` (исходный монорепо, SHA коммита-источника, список путей), `.gitignore`, `.dockerignore`.
6. **Переписать связи между репозиториями:** `Dockerfile.goweb` и `Caddyfile.goweb` берут фронт как артефакт, а не из соседнего каталога; `deploy-*.sh` — из репозитория `deploy` с указанием версий образов; `tests/` и `docs/` — ссылки на новые пути.
7. **Параллельный период.** GitHub-монорепо остаётся источником боевого деплоя, пока новые репозитории не пройдут свои пайплайны и живую приёмку из `docs/BROWSER_CALL_ACCEPTANCE.md`. Только затем переключить деплой и пометить GitHub-репозиторий архивным.
8. **Проверка:** зелёный пайплайн в каждом репозитории, сборка всех образов из новых репозиториев, живая приёмка звонка браузер↔браузер, запись в `BROWSER_CALL_ACCEPTANCE.md`.
