# Nateks VoiceCom VC-110-1: подключение к домашней сети

Проверено 12 октября 2026 года для шлюза с маркировкой `FG-ACE-VC-110-1`
(два порта FXO, один WAN, четыре LAN). Это инструкция по **сетевому доступу к
шлюзу**. Подключение городской линии, настройка SIP/Asterisk и звонки в рамках
этой работы не выполнялись и не проверялись.

## Схема подключения

```text
домашний Wi-Fi-роутер, LAN ── Ethernet ── WAN  Nateks
компьютер, Ethernet          ── Ethernet ── LAN1 Nateks (для настройки)
```

Управление через LAN1 доступно по `http://192.168.8.254/`. WAN получает адрес
от домашнего роутера по DHCP. На момент проверки это был
`http://192.168.20.236/`; **адрес может измениться** после новой выдачи DHCP.
Сам домашний роутер в этой работе не меняли и DHCP-резервирование для шлюза
не создавали. Если нужен постоянный адрес, закрепите за шлюзом адрес в DHCP
роутера, сверив MAC именно в его текущей таблице аренды.

## Почему шлюз сначала не получал адрес

WAN был настроен статически: `192.168.1.2/24`, шлюз `192.168.1.254`, ручной
DNS `168.95.1.1`. Домашняя сеть компьютера и роутера использовала
`192.168.20.0/24`, поэтому эта конфигурация не давала шлюзу рабочего адреса
в домашней сети. При прямом подключении WAN к компьютеру DHCP-запроса от
шлюза также не было. Это объясняется статическим режимом WAN; отсутствие
аренды само по себе не доказывало неисправность порта.

Для настройки компьютер подключили к **LAN1**, а WAN — к LAN-порту роутера.
LAN-интерфейс Nateks оставлен в режиме маршрутизатора с адресом
`192.168.8.254/24` и включённым DHCP-сервером (пул
`192.168.8.1–192.168.8.250`). Компьютер получил `192.168.8.1/24`.

## Сохранённые настройки Nateks

В веб-интерфейсе по LAN1 открыли **Сетевые Настройки** и установили:

| Параметр | Значение |
| --- | --- |
| WAN | DHCP |
| DNS для WAN | Авто |
| LAN | `192.168.8.254/24`, DHCP включён |
| WEB из WAN | Порт `80`, по явному запросу владельца для доступа с Wi-Fi |
| Web UI | Включён |
| Telnet | Выключен |

Изначально WEB из WAN был закрыт значением `0`: заводской веб-вход не имел
пароля. Перед открытием порта владелец сам задал логин и пароль в
**Дополнительные Опции → Web UI Login ID / Web UI / IVR Password**. Значения
учётных данных не хранятся в этом репозитории. Веб-доступ по WAN работает по
HTTP без TLS и доступен узлам домашней сети; не пробрасывайте этот порт в
интернет. Выбранный владельцем пароль слабый, его стоит заменить.

После изменения параметров в **Работа Системы** отметили
**Сохранить Настройки** и **Рестарт**, затем нажали **Принять**. Интерфейс
показал «Настройки сохранены» и «Система перезагружается». Параметры WAN DHCP,
DNS Auto и доступа по WAN сохранялись после отключения питания.

## Настройка компьютера для прямого доступа через LAN1

На компьютере интерфейс `enp5s0` ранее работал в режиме NetworkManager
`ipv4.method shared` и раздавал адреса из `10.42.0.0/24`. Его профиль
переключили в `ipv4.method auto`, чтобы получить адрес от LAN DHCP шлюза.
Чтобы Ethernet-шлюз не забирал маршрут по умолчанию и DNS у Wi-Fi, на этом
профиле также установили `ipv4.never-default yes` и
`ipv4.ignore-auto-dns yes`. Профиль пока оставлен в таком состоянии, пока
компьютер подключён к LAN1. Временный диагностический профиль `nateks-diag`
удалён.

Для повторения на другом компьютере найдите имя активного Ethernet-профиля
командой `nmcli -g GENERAL.CONNECTION device show <интерфейс>` и, если это
отдельное соединение только для LAN1 Nateks, примените:

```sh
nmcli connection modify '<имя-профиля>' \
  ipv4.method auto ipv4.never-default yes ipv4.ignore-auto-dns yes
nmcli connection up '<имя-профиля>'
ip -4 addr show dev <интерфейс>
```

Адрес компьютера должен быть в `192.168.8.0/24`; затем открывайте
`http://192.168.8.254/`. Не выполняйте эти команды на произвольном рабочем
Ethernet-профиле: параметры маршрута и DNS изменятся и для других сетей.

## Проверка и восстановление доступа

После последнего включения питания WAN показывал DHCP-адрес
`192.168.20.236`; компьютер по Wi-Fi (`192.168.20.164`) достигал его по
ICMP. Страницы входа на WAN и LAN1 отвечали HTTP `200`; шесть
последовательных проверок обеих сторон за примерно 30 секунд прошли.
Владелец сообщил, что **RUN мигает**, а **ALARM погас**. Это подтверждает
сетевой доступ на момент проверки, но не проверяет SIP-регистрацию,
телефонную линию или звонки.

Если `192.168.20.236` перестал открываться:

1. Проверьте текущий DHCP-адрес шлюза в роутере; прежний адрес мог измениться.
2. Проверьте WAN и LAN1 отдельно. При подключённом к LAN1 компьютере
   `192.168.8.254` должен отвечать даже без WAN.
3. Если ping работает, а HTTP-соединение устанавливается и не возвращает
   страницу, закройте старые вкладки управления и откройте новую. Во время
   этой настройки ответы HTTP восстановились сразу после закрытия зависшей
   вкладки; точная причина зависания веб-сервера не установлена.
4. Программный рестарт дважды сопровождался длительной недоступностью и
   частыми переподключениями Ethernet. Отключение питания на 15 секунд
   восстанавливало работу. **Не нажимайте RESET**: это отдельный сброс
   настроек. Если проблема повторится, проверьте питание, кабели и состояние
   устройства до дальнейшей настройки SIP.

Сетевые изменения не сопровождались обновлением Asterisk или приложений.
Обязательная приёмка браузерных звонков для проекта здесь не запускалась;
последний её результат остаётся в [BROWSER_CALL_ACCEPTANCE.md](BROWSER_CALL_ACCEPTANCE.md).
