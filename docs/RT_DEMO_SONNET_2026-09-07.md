# Живая демка на VM209: `infer/rtrvc.py` вместо офлайн-пайплайна

Дата 2026-09-07. По запросу — реализовал на VM209 метод с лучшим результатом
из [LATENCY_RESEARCH_SONNET_2026-09-07.md](LATENCY_RESEARCH_SONNET_2026-09-07.md)
как настоящий работающий сервис (не только скрипты-бенчмарки), и две демки:
голос как было (один говорящий) и несколько подключений (боты).

**Это НЕ трогает продакшен.** Отдельный процесс, отдельный порт, отдельная
модель в памяти GPU. `voice-rvc.service` (порт 8090) и conference (порт 8091)
не останавливались и не перезапускались.

## Что развёрнуто

| | |
|---|---|
| Код на VM209 | `/tmp/rt_demo/` (скопирован из `rvc_service/`+`web-rt/` этой ветки, не из деплой-пайплайна) |
| Процесс | `uvicorn rvc_service.rt_server:app --host 127.0.0.1 --port 8093`, запущен вручную (`setsid`, не systemd-юнит — по желанию можно оформить в юнит позже) |
| Слушает | только `127.0.0.1:8093` на VM209 — не торчит наружу, не в Caddy |
| Движок | `infer/rtrvc.py`, block=0.3с, extra=1.5с, crossfade=0.05с (те же числа, что в исследовании) |
| До 4 одновременных сессий | общий `asyncio.Lock` на GPU-вызовы + сброс `cache_pitch`/`cache_pitchf` при смене говорящего (см. раздел 4 основного отчёта) |
| GPU-память | 2267MiB пока сервис жив (у прод-сервиса — 1043MiB простой); хватает с запасом в 4096MiB |

## Как открыть демку прямо сейчас

Эта сессия уже держит открытым SSH-туннель `localhost:8093 → VM209:8093`
(на этом же ноутбуке, где вы читаете этот чат). Просто откройте в браузере:

```
http://localhost:8093/
```

`localhost` браузер считает безопасным контекстом даже без HTTPS, поэтому
микрофон разрешится нормально — отдельный сертификат не нужен. Если
перезапустите Claude Code и туннель пропадёт, поднимите его заново с этого
ноутбука (не требует sudo/паролей — тот же ключ, что уже используется):

```bash
ssh -N -L 8093:127.0.0.1:8093 ubuntu@192.168.20.70
```

и держите эту команду запущенной в отдельном терминале, пока тестируете.

## Демка 1 — «голос как было» (один говорящий)

Страница `http://localhost:8093/` — микрофон → тот же голос, но с блоком
0.3с вместо 2с. Наушники обязательны. Кнопки Start/Stop, индикаторы
входа/выхода, отображается фактическое время обработки блока.

Эта же связка проверена скриптом до вас (не выдумано на глаз):
`experiments/latency-sonnet/scripts/rt_stream_demo.py` прогнал 40с и 90с
реальной речи через тот же движок и код — обработка 106–119мс/блок,
без утечек памяти GPU. Живой браузер добавит к этому реальную акустическую
задержку микрофон→наушники, которую я numerically не измерял (как и в
проде — см. HANDOFF.md).

## Демка 2 — несколько подключений (часть — боты)

`experiments/latency-sonnet/scripts/bot_client.py` открывает несколько
WebSocket-сессий тем же протоколом, что и браузер, и прогоняет через них
записанную речь (`ru.wav`/`en.wav`) в реальном времени (не пачкой). Можно
одновременно открыть страницу в браузере (это будет 3-е/4-е "подключение"
живым голосом) — сервис поддерживает до 4 сессий разом.

Запуск с ноутбука (боты подключатся через тот же туннель):

```bash
ssh ubuntu@192.168.20.70 '/opt/voice-rvc/venv/bin/python3 /tmp/bot_client.py ws://127.0.0.1:8093/ws/rvc 20 /tmp'
```

**Честный результат нагрузочного теста** (полные данные и обе WAV —
`experiments/latency-sonnet/results/multi_session_demo.json` и `samples/`):

- **2 одновременных, непрерывно говорящих** бота — выдерживает бесконечно:
  оба доиграли полные 20с, обработка 145–228мс/блок, запас есть.
- **3 одновременных, непрерывно говорящих** — уже перебор: суммарный спрос
  на GPU (3 вызова каждые 0.3с) превышает пропускную способность одной
  GTX1050Ti (~1 вызов за 0.11–0.14с), и все три сессии корректно завершаются
  с ошибкой `overloaded` вместо того, чтобы копить очередь или портить друг
  другу звук — это то самое поведение, которое уже заложено в философию
  проекта (`LIVE_STATUS.md`: "перегрузка завершает сессию явно").

Это **не** жёсткий лимит "на 3 пользователя сайт падает" — боты говорят
непрерывно без пауз, реальные люди в разговоре молчат добрую часть времени,
так что живых участников с паузами в речи, скорее всего, поместится больше.
Но как честная нижняя граница на этом железе с этой конфигурацией — да,
около 2 одновременных полностью загруженных потоков.

## Что дальше и что я не стал делать сам

- Не оформил как systemd-юнит и не добавил в Caddy — сознательно: это
  research/demo-инстанс, публиковать его наружу или делать постоянным без
  вашего решения не стал.
- Не убил и не изменил `voice-rvc.service`/`conference` — только прочитал
  их состояние (`ss -tln`), чтобы не занять чужой порт (8091/8092 уже заняты
  conference/Asterisk — использовал свободный 8093).
- Если демка понравится и захотите её постоянно — на это будет отдельный
  шаг: systemd-юнит, продуманный `MAX_SESSIONS`, и обсуждение, нужен ли ей
  публичный домен вообще, или локальный туннель — с осознанным решением,
  а не по умолчанию.

## Остановить демку

```bash
ssh ubuntu@192.168.20.70 'pkill -f "uvicorn.*rt_server"'
```

Проверить, что GPU-память вернулась к простою прод-сервиса:

```bash
ssh ubuntu@192.168.20.70 'nvidia-smi --query-gpu=memory.used --format=csv'
```

Ожидается 1043MiB (столько же, сколько было до запуска этой демки).
