# Живая демка: `infer/rtrvc.py` на `voice-claude.lan.awesomeio.ru`

Дата 2026-09-07. По запросу — реализовал на VM209 метод с лучшим результатом
из [LATENCY_RESEARCH_SONNET_2026-09-07.md](LATENCY_RESEARCH_SONNET_2026-09-07.md)
как настоящий работающий сервис, на собственном домене, с двумя демками:
голос как было (один говорящий) и комната ботов (несколько собеседников,
слушать без микрофона).

**Это НЕ трогает продакшен.** Отдельный процесс на VM209, отдельная модель в
памяти GPU, отдельная запись DNS, отдельный `handle`-блок в общем Caddy
(единственное, что действительно общее — см. "Важно" ниже).
`voice-rvc.service` (порт 8090) и `conference` (порт 8091) не
останавливались и не перезапускались мной ни разу.

## Открыть прямо сейчас

```
https://voice-claude.lan.awesomeio.ru/                 — список всех вариантов голоса
https://voice-claude.lan.awesomeio.ru/v1-rmvpe/        — вариант 1: RMVPE, блок 0.3с (сегодняшний дефолт)
https://voice-claude.lan.awesomeio.ru/v2-fcpe/         — вариант 2: FCPE, блок 0.3с (~28% быстрее питч)
https://voice-claude.lan.awesomeio.ru/v3-rmvpe-fast/   — вариант 3: RMVPE, блок 0.15с (агрессивно)
https://voice-claude.lan.awesomeio.ru/v4-fcpe-fast/    — вариант 4: FCPE, блок 0.15с (максимально агрессивно)
https://voice-claude.lan.awesomeio.ru/bots/            — комната ботов, слушать без микрофона
```

Работает как обычный сайт с настоящим сертификатом (используется тот же
wildcard `*.lan.awesomeio.ru`, что и у продакшена) — открывается в любом
браузере через ваш VPN, никакого туннеля больше не нужно.

Все 4 варианта голоса — это ОДИН и тот же загруженный движок/модель на
VM209 (память GPU не растёт от их количества — веса общие), просто каждый
подключается к своему WebSocket-пути (`/ws/rvc/v1-rmvpe` и т.д.) с разными
`block_time`/`f0method`. Переключаться между ними можно свободно, играя по
очереди — сравните, какой звучит лучше и какой первым "спотыкается".

На каждой странице голоса есть ползунок **"Доп. задержка, сек"** (0–10с,
по умолчанию 0) — тот же приём, что в оригинальной проде: ставит фикс
задержку ПЕРЕД тем, как обработанный звук уйдёт в наушники (реализовано в
`web-rt/audio-worklet.js` как кольцевой буфер, идентично оригинальному
`web/audio-worklet.js`). Это не имеет отношения к задержке самого
конвейера — просто добавляет к ней запрошенное число секунд, для эффекта
или тестирования.

## Что развёрнуто

| | |
|---|---|
| DNS | `voice-claude.lan.awesomeio.ru A 192.168.20.70` — добавлена одна запись в `records.tsv`-зону на VPS `evita` (`pdnsutil replace-rrset`), остальные записи не трогал |
| Код на VM209 | `/tmp/rt_demo/` (скопирован из `rvc_service/`+`web-rt/` этой ветки, не из деплой-пайплайна) |
| Процесс | `uvicorn rvc_service.rt_server:app --host 127.0.0.1 --port 8093`, `PYTHONPATH=/tmp/fcpe_pkgs` (нужен вариантам 2/4 с FCPE), запущен вручную (`setsid`, не systemd-юнит) |
| Слушает | только `127.0.0.1:8093` на VM209 — снаружи недоступен напрямую, только через Caddy |
| Caddy | добавлен свой `handle`-блок для `voice-claude.lan.awesomeio.ru` → `reverse_proxy 127.0.0.1:8093` в **общий** `/etc/caddy/Caddyfile` — см. "Важно" |
| Движок | `infer/rtrvc.py`, один загруженный экземпляр на все 4 варианта (`rvc_service/rt_server.py: VARIANTS`), crossfade=0.05с/search=0.02с общие |
| До 4 одновременных сессий | общий `asyncio.Lock` на GPU-вызовы + сброс `cache_pitch`/`cache_pitchf` при смене говорящего или f0method |
| GPU-память | 2355MiB пока сервис жив (у прод-сервиса — 1043MiB простой) — чуть больше, чем без FCPE (2267MiB), т.к. теперь резидентны обе питч-модели; хватает с запасом в 4096MiB |

## Важно: общий Caddyfile, и там кто-то ещё активно работает

Пока я это делал, `/etc/caddy/Caddyfile` **дважды перезаписывался чужим
деплой-скриптом** (продакшен `voice-rvc` передеплоился минимум 4 раза за
последние ~15 минут этой сессии — релизы `20260907T065444Z`,
`065807Z`, `070310Z`, `070630Z` — то есть кто-то ещё, скорее всего другой
ИИ-агент, прямо сейчас активно катит изменения в тот же `voice-rvc.service`
и его Caddy-конфиг, судя по появившемуся там новому `/ws/rvc-v2`). Их скрипт
генерирует Caddyfile из своего шаблона **без** моего блока и перезагружает
Caddy — оба раза это стирало мою запись для `voice-claude`.

Сейчас (на момент записи этого документа) блок на месте и домен работает —
проверено end-to-end: `/healthz`, `/`, `/bots/`, WebSocket `/ws/listen`, и
продакшен `vm-voice-1.lan.awesomeio.ru` продолжает отвечать 200 в течение
всего этого. Но **если домен вдруг перестанет открываться** — вероятнее
всего, их очередной деплой снова переписал файл. Проверить и починить:

```bash
ssh ubuntu@192.168.20.70 'grep -q voice-claude /etc/caddy/Caddyfile && echo present || echo MISSING'
```

Если `MISSING` — восстановить одной командой (безопасно: только
добавляет блок в конец файла, ничего существующего не трогает):

```bash
ssh ubuntu@192.168.20.70 "cat <<'EOF' | sudo tee -a /etc/caddy/Caddyfile
https://voice-claude.lan.awesomeio.ru {
    bind 192.168.20.70
    tls /etc/voice-certs/fullchain.pem /etc/voice-certs/key.pem
    reverse_proxy 127.0.0.1:8093
}
EOF
sudo caddy validate --config /etc/caddy/Caddyfile && sudo caddy reload --config /etc/caddy/Caddyfile --force"
```

Я не пытался договориться с тем скриптом/агентом или зафиксировать это
навсегда в их шаблоне — это чужой активный чек-аут, трогать его код было бы
рискованнее, чем изредка руками восстанавливать одну строчку. Если это
станет раздражать — стоит либо согласовать с тем, кто гоняет эти деплои,
либо перенести мою демку на постоянный SSH-туннель (`localhost`, как было
изначально) — это полностью иммунно к их перезаписям, просто без красивого
домена.

Прямой альтернативный порт (в обход Caddy) я тоже проверял — **не работает**:
фаервол между VPN и LAN VM209 пропускает только 22 и 443, так что без
общего Caddy на 443 внешне достучаться нельзя в принципе.

## Демка 1 — «голос как было» (один говорящий)

`https://voice-claude.lan.awesomeio.ru/` — микрофон → тот же голос, но с
блоком 0.3с вместо 2с. Наушники обязательны. Кнопки Start/Stop, индикаторы
входа/выхода, отображается фактическое время обработки блока.

Эта же связка проверена скриптом до вас (не выдумано на глаз):
`experiments/latency-sonnet/scripts/rt_stream_demo.py` прогнал 40с и 90с
реальной речи через тот же движок и код — обработка 106–119мс/блок, без
утечек памяти GPU. Живой браузер добавит к этому реальную акустическую
задержку микрофон→наушники, которую я numerically не измерял (как и в
проде — см. HANDOFF.md).

## Демка 2 — комната ботов (несколько собеседников, слушать)

`https://voice-claude.lan.awesomeio.ru/bots/` — **микрофон не запрашивается
вообще**. На сервере зациклены две записанные фразы (`ru.wav`/`en.wav`),
каждая идёт через тот же `infer/rtrvc.py` (тот же общий GPU-движок и
блокировка, что у демки 1 — отдельной модели под ботов не грузил, чтобы не
плодить копии в те же 4ГБ VRAM), результаты сводятся (простое сложение
сэмплов) и транслируются всем слушателям разом по WebSocket
(`rvc_service/rt_bots.py`). Нажали «Слушать» — играет то, что говорят боты
прямо сейчас, без записи и без сохранения.

Отдельно, скриптом с ноутбука можно устроить нагрузочный тест таким же
протоколом, что у реального клиента (`experiments/latency-sonnet/scripts/
bot_client.py`, три параллельные "боты"-сессии — это самостоятельный тест
многосессионности демки 1, не то же самое, что комната ботов):

```bash
ssh ubuntu@192.168.20.70 '/opt/voice-rvc/venv/bin/python3 /tmp/bot_client.py ws://127.0.0.1:8093/ws/rvc 20 /tmp'
```

**Честный результат этого нагрузочного теста** (полные данные и WAV —
`experiments/latency-sonnet/results/multi_session_demo.json` и `samples/`):

- **2 одновременных, непрерывно говорящих** — выдерживает бесконечно: оба
  доиграли полные 20с, обработка 145–228мс/блок, запас есть.
- **3 одновременных, непрерывно говорящих** — уже перебор: суммарный спрос
  на GPU (3 вызова каждые 0.3с) превышает пропускную способность одной
  GTX1050Ti (~1 вызов за 0.11–0.14с), и все три сессии корректно завершаются
  с ошибкой `overloaded` вместо того, чтобы копить очередь или портить друг
  другу звук — то самое поведение, что уже заложено в философию проекта
  (`LIVE_STATUS.md`: "перегрузка завершает сессию явно").

Это не жёсткий лимит "на 3-го пользователя сайт падает" — боты говорят без
пауз, живые люди молчат добрую часть разговора, так что участников с
паузами в речи, скорее всего, поместится больше. Но как честная нижняя
граница на этом железе — да, около 2 одновременных полностью загруженных
потоков разом с демкой 2 (комната ботов сама потребляет часть этого же
бюджета, раз использует тот же движок).

## Что дальше и что я не стал делать сам

- Не оформил как systemd-юнит — сознательно: это research/demo-инстанс,
  делать его постоянным (переживающим перезагрузку VM) без вашего решения
  не стал.
- Не убил и не изменил `voice-rvc.service`/`conference` — только прочитал их
  состояние (`ss -tln`, `qm config`), чтобы не занять чужой порт (8091/8092
  уже заняты conference/Asterisk — использовал свободный 8093) и не мешать
  их работе.
- Не стал чинить/координировать с чужим деплой-скриптом, который перезаписал
  Caddyfile дважды (см. "Важно" выше) — это чужой активный чек-аут.
- Не переключил FCPE — оставил решение на прослушивание.

## Остановить демку

```bash
ssh ubuntu@192.168.20.70 'pkill -f "uvicorn.*rt_server"'
```

Проверить, что GPU-память вернулась к простою прод-сервиса:

```bash
ssh ubuntu@192.168.20.70 'nvidia-smi --query-gpu=memory.used --format=csv'
```

Ожидается 1043MiB (столько же, сколько было до запуска этой демки). DNS-запись
`voice-claude` и Caddy-блок при этом останутся (просто перестанут получать
ответ от несуществующего процесса) — если захотите убрать их полностью,
это отдельная просьба, сам не удалял, чтобы не гадать, что от этой демки
хочется оставить.
